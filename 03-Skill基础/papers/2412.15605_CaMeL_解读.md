# 《CaMeL: Defeating Prompt Injections by Design》解读

| 项目 | 内容 |
|---|---|
| 作者/机构 | Sahar Abdelnabi 等，CISPA |
| 发表 | arXiv:2412.15605（2024.12） |
| 一句话总结 | 把"数据即指令"的提示注入问题形式化为**信息流控制**问题：给 agent 的每个组件打标签，运行时强制"不可信数据永远不能流向指令槽"——从架构上根治注入 |

## 1. 研究背景与问题

- 间接提示注入：网页/邮件/文档里的恶意文本劫持 agent（InjecAgent 基准显示主流 agent 大范围中招）。
- 现有防御（过滤、提示加固）是对抗性的、可被绕过。
- 问题：**能否从系统设计层面保证注入不可能生效？**

## 2. 核心方法

1. **标注（Annotation）**：给每条信息打标签——"来自用户的指令"vs"来自工具/网页的数据"。
2. **信息流控制**：运行时用 taint tracking 强制约束：不可信数据不允许进入指令上下文槽位（如 system prompt、工具选择参数）。
3. **责任分离**：规划器只信用户指令通道；执行器拿到的不可信数据被隔离标签包裹。
4. 配套新攻击面分析（如多轮泄漏、工具返回值投毒）。

## 3. 关键实验与结果

- 在多种注入攻击（直接/间接/多轮）下保持安全，同时任务成功率几乎无损。

## 4. 局限性与争议

- 需要修改 agent 框架（非纯提示方案）；标签传播在复杂工具链上有工程成本。
- 解决"注入"不解决"技能本身作恶"。

## 5. 与本知识库的关联（Skill 视角）

模块 03 第 7 节"合规与安全 + 技能审计"的核心参照：当 skill 可以引用 skill、读外部资源时，**能力（capabilities）必须带权限标签**——本环境"skill 声明所需工具，运行时白名单校验"的学理来源。

## 6. 阅读建议

- 精读 §3（威胁模型）与 §4（设计）。无需复现，但要记住一句话：**"Data is not instructions" 应该由运行时保证，而不是靠模型自觉。**

## 1. 研究背景与问题

- 已有工作测 agent"修不修得好代码"，但 harness（上下文组装、工具、状态、验证）本身正成为能力的主要来源（模块 05 的主题）。
- 问题：**LLM 能创造 harness 吗？能进化它吗？进化出的机制在 held-out 任务和换执行器时还活着吗？**

## 2. 核心方法

- **两阶段**：Creation（从自然语言需求从零构建可运行 harness，用 Unified-Eval 保证跨执行器可移植）→ Evolution（用下游执行反馈迭代，产出**冻结的版本化**候选）。
- **评测对象是被评测的 harness 本身**：反馈集（trajectory 中反复评）与 held-out 集（SWE-Pro 630 题 + Terminal-Bench 89 题，结果永不回流）严格分离；另设"固定 Gemini 执行器"消融。
- 9 条 lineage、73 个正式版本、64 次相邻版本切换全轨迹分析。

## 3. 关键实验与结果

- **机制存活率惊人地低**：11/18 声明了 State 类、1/18 有状态保存接口、1/18 有周期 checkpoint；26,679 条任务轨迹里 checkpoint 事件为 0——**18/108 个组件从未在运行时被触发，且全部是状态/记忆类**。
- **编辑偏好**：64 次切换集中在执行流/控制（58）、工具（37）、生命周期恢复（17）；状态管理（4）、独立验证器（16）几乎不动。
- **泛化断裂**：可见分与 held-out 分仅 34/64 一致；9 个自报"最终版"仅 2 个是 held-out 最优；固定执行器下 4 条 lineage 只有 Opus 自己不退化。

## 4. 局限性与争议

- 创建分析只覆盖 18 个 Code 工件；触发 ≠ 有用；post-freeze held-out 只测了 SWE-Pro。
- 结论最强的一刀切在"工程实践"层面：agent 擅长改流程，不擅长给自己建记忆与验证。

## 5. 与本知识库的关联

模块 06 主线之③；模块 05 的"严格化版本"——把 SWE-agent 的 ACI 思想推进到"harness 作为被评测工件"；也是模块 03 技能审计（机制是否真的被调用）的实证支撑。

## 6. 阅读建议

- 先读 §3.2（Creation）与 §4.2/4.3（Evolution 与评测协议）——反馈集/held-out 集/固定执行器三件套设计值得所有自进化系统照搬。
- 记住一句话：**代码里存在 ≠ 运行时活着；留存需要版本化 + 回滚 + held-out 验证。**
